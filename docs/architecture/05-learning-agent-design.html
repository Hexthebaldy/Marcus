01 · 用户会得到什么

用户在 Discover 收藏了几篇摄影展，下次点击悬浮入口时，Marcus 可以先给出“这个周末看摄影展”的方向。用户也能打开“我的偏好”，看到这条判断来自哪些收藏，直接修改或删掉它。

本方案把这些动作接到现有 React Native 客户端、FastAPI 服务和 MySQL 数据库中。后台先保存用户做过什么，再整理哪些偏好值得保留；推荐时读取这份可修改的偏好。模型本身的参数不会因此被训练或改写。

交付范围：这是一份待实现的技术方案。下文逐项区分 Hermes 源码事实、Marcus 已有代码与建议新增内容。没有把方案中的路由、表或模型能力写进现有应用。

点开就有方向

先展示三个结合当前内容和已有偏好的选项；支持随时输入文字。不会要求用户先面对一个空白输入框。

一次需求单独保存

“今晚、静安、150元以内”只约束这次推荐。只有用户确认“以后也这样推荐”，或积累了足够行为证据，才进入长期偏好。

每条记忆可以改

“为什么觉得我喜欢摄影展”能展示日期和对应内容。删除后，旧后台任务不能把它重新写回。

首发按上海设计；沿用邮箱登录、地点与活动两种编辑内容重心、独立的用户 Notes。Agent 推荐结果存放在自己的对话中，不创建 EditorArticle，也不替用户发布 Note。

之前第一版已移除 Agent；本文件描述之后重新加入 Agent 的独立阶段。原有 Discover 排序和发布流程先保持现状，Agent 的推荐结果单独呈现。

Hermes 收到一句话后，实际做了什么

  1. 先确认这段会话没有被另一个执行者占用。接入代码调用 run_conversation。对于已有数据库会话，Hermes 先向数据库登记“这一轮由我执行”；如果别人正在执行，就等待，取得运行权后重新读取最新历史。这避免两个执行者各拿着旧历史，同时回答和写入同一会话。run_turn_runner.py:1726；turn_facade_lease.py:238

  2. 准备这次要交给模型的内容。Hermes 在历史末尾追加用户这句话，恢复这段会话固定的系统提示，检查历史是否太长，再读取与本次问题相关的记忆。配置外部记忆提供者时，查询得到的补充资料放进本轮消息；内置文件记忆通常仍用会话建立时的快照，不是每轮都重读或重写系统提示。随后保存本轮输入。turn_context.py:1046、turn_context.py:1124

  3. 模型需要查资料时，由 Python 执行查询。模型返回工具名称和参数；Hermes 检查这个工具是否允许使用，在启用会话数据库的路径中，先把调用要求存进数据库，再执行对应函数。函数返回的结果也先保存，然后交回模型。模型可以继续查资料，也可以结束并给出回答。工具调用要求保存失败时，Hermes 不会继续执行工具。conversation_loop.py:1535；turn_tool_round.py:116

没人要求“记住”时，后台怎样整理

内置记忆默认每十轮检查一次：工具可用、记忆存储存在，而且本轮有非空回答、未中断且满足复盘配置时，程序可以启动一个后台 Agent，阅读刚才的对话副本，选择值得保存的内容。后台 Agent 不把自己的复盘指令写进用户聊天。技能整理另按工具迭代次数触发，保存的是“以后怎样完成一类任务”。计数条件 · 触发后台复盘

04 · 哪个进程负责哪一步

用户点选“周末看展”后，手机向 FastAPI 发一个请求。FastAPI 只创建一次运行记录和一条 MySQL 任务，提交后立即返回运行编号。另一个 Python 进程读取任务，查询内容并调用模型。手机按运行编号读取进度和结果。

手机 App当前视口、选项、文字
→
FastAPI鉴权、校验、保存请求
→
MySQLrun + job 已提交
→
Agent worker查内容、调用模型、保存结果

手机每隔约 1 秒查询一次运行状态；切到后台后暂停，重新打开页面再查询同一个编号。首期用这种简单的轮询方式，不依赖移动端持续保持一条流式连接。关闭页面不会自动撤销已提交的请求；“停止生成”按钮才发取消请求。

运行的程序 读取哪些任务 调用谁 / 写入哪里
FastAPI HTTP 进程 不执行长模型任务 现有登录依赖取得 user_id；事务内保存消息、run 和 job。
原有 jobs.worker 只读取 queue_name=default 继续发邮件、处理媒体、审核和已有清理。
jobs.agent_worker --queue agent 只读取 queue_name=agent 调用 agent_runtime_service；外部调用期间不占数据库事务。初期一个进程同时跑2个 run。
jobs.agent_worker --queue learning 只读取 queue_name=learning 整理学习批次、处理记忆维护；初期并发1，避免挤占前台模型配额。
同一个 MySQL 实例 保存所有业务与任务行 一笔事务可以同时保存用户动作和行为事件，不再另加消息中间件。
已有 Redis 仍负责短期限流等现有用途 不把它当唯一记忆存储或本方案的任务队列。

这些程序继续共用一个代码库和数据库，部署时只是启动不同命令。没有引入需要单独网络协议、版本发布和数据所有权的微服务。独立进程的目的，是让一次几十秒的推荐不挡住验证码邮件。

LangChain 只放在模型调用处

推荐流程把消息与允许使用的工具说明交给 agent_model_service.py，由这个文件使用 LangChain 的聊天模型接口请求供应商，返回统一的“文本、工具请求、用量”。异步调用、工具绑定与结构化输出能力由适配器使用；数据库事务、用户权限、任务重试和记忆删除仍由 Marcus 代码决定。工具选择和最终结构化成稿分成两次模式，避免假定任意供应商都支持二者同时启用。

先接一个通过兼容测试的供应商，固定依赖到 uv.lock。供应商、模型名、部署地区和额度是配置项；本方案不假定当前账号已开通某模型。暂不使用 LangGraph、外部记忆服务或向量数据库。相关能力依据 LangChain 官方模型文档；需要在实施时针对选定供应商测试，而不是只看“兼容”标签。

05 · 一次推荐怎样完整执行

从当前页面到三个方向

Discover 向入口提供当前城市、区、Tab，以及最多 10 个真正出现在屏幕上的内容编号。服务器重新检查这些内容是否仍公开可见，读取用户允许使用的偏好，再从固定方向模板中挑三个。例如有足够展览内容时给出“周末看展”，有现场演出时给出“今晚听现场”。没有足够内容就给通用方向，不编造可去的地点。

入口不调用模型，返回三个稳定的方向编号、文案和过期时间。选项提交后，服务器重新校验条件，不信任前端传回的推荐理由。用户也可以直接输入文字。

点击方向后，数据库和模型各做什么

  1. 手机提交一次选择。请求包含客户端生成且重试沿用的 request_key、会话编号或空值、方向/文字和本次条件。不包含可随意指定的 user_id。
  2. HTTP 接口先结束数据库工作。登录依赖给出真实用户；service 在短事务里检查账号、幂等键、当前活动运行，新增 conversation（需要时）、user message、run 和 job。事务提交后返回 202 + run_id。同一键换了正文返回409，同一键同正文返回已有run。
  3. Agent worker 领取 job。更新租约持有人和递增的 lease_generation，提交领取事务。然后再读取本次条件、当前有效偏好和可见内容，形成只供这一次运行使用的 Python 数据对象。
  4. 缺少必要条件时直接给选项。例如演出时间未定，就返回“今晚 / 周末 / 自选”。一次最多问3项，用户可跳过。这个run以 succeeded 结束，result.kind=question；等用户点击才创建下一run，不让worker一直等待。
  5. 需要理解文字或补查询时调用模型。runtime 先保存 model step 和预算预留，提交事务，再把有长度限制的消息交给模型。收到工具请求后，只允许固定工具名和通过校验的参数。
  6. Python 查询工具真正读取数据。runtime 保存 tool step 后执行查询。工具根据服务器持有的 user_id 检查公开状态、屏蔽、场次时间；模型只能请求查询，不能执行SQL。结果先保存，再传回下一次模型调用。
  7. 模型组织推荐，代码核验事实。成稿只能引用候选编号。代码再次验证公开状态、当前版本、场次和价格，把标题、地址、日期、媒体地址从数据库填入。未知营业时间就标“需确认”，不能让模型补写。
  8. 保存前重新检查是否仍有权写。短事务锁用户设置行，检查账号、privacy_epoch、run状态和当前job租约编号；通过后保存assistant消息、推荐项、run结果，释放活动run指针，提交。失败则丢弃迟到的结果。
  9. 手机取回结构化结果。服务器读取时再次校验用户、epoch和内容可见性。后台学习只读取用户输入和真实动作，不把生成的推荐文章当作用户偏好。

状态、取消与故障

queued → running → succeeded / failed / cancelled / expired
running → queued：仅在期限内、预算够且错误允许重试时
终态不能回到 running；点“重试”建立新 request_key 和新 run

模型限流或暂时网络错误最多做一次受控重试；认证失败、未知工具、越权参数不重复请求。重试前先检查deadline、调用次数和预算。默认不在另一供应商悄悄重发个人上下文；备用模型需要明确配置并经过相同数据策略检查。

用户取消后，事务先标记 run=cancelled，再取消对应job并增加其租约编号；worker 尝试中断网络请求。网络请求可能已经在供应商处执行或计费，所以“取消成功”表示 Marcus 不再接受结果，不承诺撤销外部计算费用。

worker 崩溃后，新worker接管过期租约。已成功且输入指纹相同的步骤可以读取结果继续；内容工具恢复时重新检查可见性。开始调用却没有收到结果的 model step 标为 unknown，按已预留额度计费；预算允许时另建尝试，绝不假装它没有发生。只读工具允许重跑；首期没有购票、发布或自动收藏这类外部写入工具。

续租失败时，旧worker设置本地取消标记，尽力关闭当前模型连接，并且不再启动后续模型或工具步骤。它不能把共享run改为cancelled，也不能清除active_run_id，因为新worker可能已经接管。旧步骤的未知费用由当前持有者或维护任务核对；迟到回复只能按step编号幂等结算用量，不得保存私人正文。

额度执行顺序必须固定：事务内预留额度并保存step=prepared；发请求前另开短事务重新核对epoch、run和租约，将仍为prepared的step改为running并提交；最后才发网络请求。清理任务也锁同一step，仅仍为prepared时，在同一事务把它改为failed、写error_code=not_dispatched及accounted_at并退回额度；迟到worker再尝试prepared→running就会失败。一旦进入running，即使恰好在网络发送前崩溃，也保守按unknown处理。

不锁着数据库等待模型。现有 HTTP 的 db 会在接口结束时提交；如果直接在其中等待模型，用户行可能一直被锁住。这里每段“读快照 / 登记步骤 / 写结果”都各自提交。租约检查与用户删除检查必须和写结果放在同一笔事务，不能先查一下、关掉事务、再另开事务写。

后台什么时候学习

  1. 只有 memory_mode=behavior 才记录用于长期学习的行为。事件最多合并2分钟或20条后生成一批；用户明确设置偏好直接同步保存，不等待批次。
  2. learning worker 定时扫描尚未分配批次的事件，使用行锁领取固定的一组，创建 agent_learning_batches，并在同一事务插入目标为 batch_id 的job。处理标记按事件行保存，不用“最大ID”当游标，以免并发事务提交顺序不同造成遗漏。
  3. 标签、动作计分优先用规则完成。用户原话只在出现“记住 / 以后 / 通常”等意图且范围可表达时，交给模型提取候选；模型必须给 source_message_id 与原文片段位置，代码验证它确实来自该用户原话。候选给用户确认后才成为explicit。
  4. worker 根据证据去重键重复执行也只生成一条贡献。保存前锁同一用户设置行，核对privacy_epoch与memory_mode，再读取尚有效的事件，合并证据并重新计算偏好。profile_revision递增，下一次推荐重新读取。
  5. 没有新证据就不问模型。学习失败不影响收藏成功；任务有限重试，失败可观测，不能把丢失学习伪装成已经记住。

原话学习有单独的持久来源：A阶段用户点击“从这句话保存偏好”时，memory_service在短事务中建立source_kind=message的batch，引用本人user消息，再登记learning队列任务。原话明确要求“记住/以后”时，也可在run完成事务中安排同一批次；唯一键保证不会因两条入口重复。message批次event_count=0，explicit模式即可执行；behavior批次必须处于behavior模式。源消息删除、超期或epoch变化时取消批次。自然语言模型只创建7天内可确认的proposed，不直接改长期偏好，调用照常记入该用户的步骤和配额。

用户确认候选时，事务检查本人、proposed状态、未过期、来源尚有效、当前epoch与版本；转成confirmed_message/active，设置confirmed_at，取消候选的7天期限或改成用户指定期限，把偏好设为explicit且user_locked，并撤销同键旧明确证据。原聊天自然到期或用户删除对话前，已经独立确认的事实原位转为manual、断开消息外键，保留确认日期和标准化值，不保留原文；未确认候选直接清理。

首期不分析上传图片里的私人信息，不推断健康、宗教、收入、性取向、住址等敏感属性；也不把举报、屏蔽作者或模型自己写的文案当作兴趣证据。历史收藏导入默认不做，用户单独选择后才导入当前仍有效的状态，并标记“导入时观察到”，不捏造过去的行为时间。

07 · 怎样挑内容并生成可用结果

服务器先按城市、公开状态和本次明确条件找候选，再让模型在这些候选内写推荐理由。它不先让模型随意想几个地点，再到数据库里勉强匹配。

  1. 先检查能不能展示。内容已发布、作者active、未被当前用户屏蔽；文章只使用当前公开版本。活动与场次必须可用，scheduled且时间与本次窗口重叠；closed地点不能作为当前可去地点推荐。
  2. 再检查本次硬条件。城市、区、时间、用户明确说的预算上限。价格unknown不当免费；严格预算下剔除未知价格，放宽需让用户选择。只有起价低于预算也不能声称整场票价符合预算。
  3. 再排顺序。明确喜欢的主题+30、明确偏好区域+10、推断主题最多+15、当前视口关联主题+8；编辑排序与新鲜度归一到0–10。当前请求可显式临时覆盖长期avoid，缺少这种明确操作时仍排除avoid主题。
  4. 减少重复。同一活动/地点最多一个主要推荐项，最近24小时已展示候选最多减10分；已去过的活动不再作为即将参加的活动。一次取最多20个候选，最终推荐3–5项；至少留一个不依赖推断偏好的合适候选。
  5. 最后成稿。模型只生成标题、导语、有限段落与候选引用编号。地点地址、场次、价格和跳转目标由后端填充。没有可信候选时返回empty和可放宽的条件，不生成虚构清单。

上述加分与阈值是首轮可调规则，不是训练得到的最优参数。时间统一使用 cities.timezone 解释；上海界面显示 Asia/Shanghai，数据库保存UTC时间。地点只有 opening_hours_text，不能可靠计算当天是否营业；没有路线数据时不声称“步行8分钟可到”。

09 · 接口与请求结构

所有接口以 /v1 开头，沿用现有Bearer登录凭证和错误格式。后端从 current_user 取得用户，前端不能在正文里替换user_id。对不属于自己的conversation/run/preference/item统一返回404，避免泄露是否存在。

方法与路径 请求中有什么 响应与具体行为
POST /agent/entry city_id、district_id?、tab、visible_contents≤10；每项type/id/version 200，三个direction{id,label,constraints_hint}、expires_at、privacy_epoch、profile_revision、memory_mode；供创建run使用。无模型调用，不存曝光。
POST /agent/runs request_key；conversation_id?；input:{kind:text或direction或choice,...}；context:{city_id,district_id?,visible_contents?}；expected_privacy_epoch 202 RunAccepted{id,status,conversation_id}；短事务建消息/run/job。同键同正文返回已有编号，不重复调模型。
GET /agent/runs/{id} 无正文 200 RunView，status/stage/result?；后台继续运行时result为空。结果中的来源重新授权。
POST /agent/runs/{id}/cancel 无正文 200同一run状态；重复取消仍成功，已成功的run不会被改回取消。
GET /agent/conversations cursor?、limit≤20 200分页对话列表，只返回本人；不返回全文模型上下文。

GET /me/agent-memory 无正文 200 memory_mode/profile_revision/privacy_epoch/preferences/proposals；偏好与候选分开显示。
GET /me/agent-memory/{preference_id}/evidence cursor? 200证据分页：动作、日期、可见内容引用；来源不可见时不给原正文。
PUT /me/agent-memory/preferences dimension/key/scope/value、expected_profile_revision、expires_at? 200 Preference；校验目录值，创建或替换明确设置，解除同键suppression，递增版本及epoch。
POST /me/agent-memory/proposals source_message_id、expected_privacy_epoch 202 batch_id；用户点“从这句话保存偏好”后建立message型批次；同消息同版本不重复。off模式先提示启用explicit。
POST /me/agent-memory/proposals/{id}/confirm expected_profile_revision、修正后的value? 200 Preference；确认本人未过期且当前epoch的proposed证据，写明确偏好；确认是普通业务操作，不是模型直接写库。
DELETE /me/agent-memory/preferences/{id} expected_revision 204；撤销证据、建立抑制标记、清理相关上下文并取消旧run；单条删除不依赖长模型调用。
PATCH /me/agent-memory/settings memory_mode、expected_profile_revision、consent_version? 200 Settings；开启behavior必须显式提供当前说明版本；切换即时失效旧任务。
DELETE /me/agent-memory expected_profile_revision 204；关闭长期记忆、清空内容及相关上下文，建立必要禁止重学标记；可重新开始但不导入旧历史。
POST /me/agent-memory/restart memory_mode、consent_version?、expected_profile_revision 200 Settings；用户主动“重新开始了解我”，清抑制、重设learning_since；仍不恢复旧数据。
POST /agent/behavior-events privacy_epoch、events≤50:{event_key,kind,target,observed_at,visible_ms?} 200 accepted/duplicates/ignored；只收前台弱信号。旧epoch/超过24小时/时间未来异常忽略并返回原因。
PUT /agent/recommendation-items/{id}/feedback request_key、kind、reason? 200 Feedback；只允许本人项；同事务保存实际变化事件。

entry响应给出expected_privacy_epoch的来源。用户改记忆后服务器返回409，手机必须刷新入口与条件并要求重新提交，不能把旧上下文静默换成新epoch继续生成。

多设备编辑用expected_revision或expected_profile_revision检查是否仍基于最新版本；不同返回409并附新版本，前端刷新后让用户重新操作。额度不足返回429和可重试时间；已过期运行返回其终态，不让手机无限轮询。幂等键不是鉴权凭证，结果查询仍然要检查当前用户。

11 · 更正、遗忘与账号删除

用户点“忘记摄影展偏好”时，服务器先锁住该用户的设置行，把 privacy_epoch 从例如12改成13，再移除偏好、撤销支持它的证据并添加抑制键。带着12号上下文的旧worker即使随后拿到模型回复，也不能再保存推荐正文或偏好。

privacy_epoch只阻止旧任务使用旧资料，不代表其他已确认且未删除的偏好一律作废。有效的已接受证据仍按状态、来源和到期时间使用；尚未处理的旧epoch事件与批次则丢弃。普通自动学习只增加profile_revision；用户主动修改数据才增加privacy_epoch。

用户操作 立即在短事务内完成 后续清理与使用限制
更正 / 忘记单条偏好 锁User再锁settings；epoch与profile_revision加1；修改或删除偏好；撤销对应证据；忘记时创建标准键suppression；取消旧run/batch。 使全部旧Agent结果与摘要失效；移除该证据引用的消息片段及相关模型输入快照。保留未涉及的历史只供本人查看，不再送进新epoch的模型上下文。
切换为explicit 不再采集/使用推断行为偏好；旧待学习任务取消；明确偏好保留。 撤销全部behavior来源active/proposed证据，删除推断偏好，未处理事件invalidated。重开behavior只接新的learning_since之后事件，旧revoked证据不恢复。
切换为off 不读取或新增任何长期偏好；取消旧epoch工作，撤销行为证据并删除推断偏好。 原明确偏好可保留但停用，界面说明“已暂停，尚未删除”；需要删除时使用清空。新对话仍可按用户本次条件推荐。
清空全部记忆 模式改off；偏好与证据删除；相关个人上下文立即不可读。 清理对话原文、推荐结果、摘要和步骤正文；保留最小抑制键及无正文额度账本。恢复时必须明确选择重新开始，不复扫旧收藏。
删除一段对话 撤销该对话运行；删除消息与摘要、未确认候选及相应来源贡献。 界面写明：曾单独点击“保存为偏好”的设置是独立条目，在偏好页管理。不会把已清理原话重新当新证据。
注销账号 在现有delete_me事务内将账号不可用、epoch加1、终止run/batch并登记Agent清理。 立即拒绝所有读取；后台删Agent私人行与正文，不沿用现有内容30天延迟来继续使用偏好。业务内容清理仍按原流程。
退出登录 / 换账号 客户端取消轮询和在途上报，清query缓存及内存事件。 长期记忆属于账号，不因普通logout删除；服务端每次读取仍验证登录，不能使用旧缓存串账号。

新run遇到epoch变化时，不把旧摘要、旧助手结果或含有旧偏好解释的历史重新拼回模型。首期采用保守做法：清空这段对话的运行上下文和旧条件，界面请用户确认当前条件后再继续；旧用户原文只按删除范围保留供本人查看，绝不自动回填为记忆。清理任务只可重复删除，不能创建新偏好。

所有Agent写路径采用一致顺序：需要用户行时先User，再settings，再当日quota，再conversation/run或batch，再job与步骤/证据行。已有互动代码也需在内容行锁之前取得这套必要前置锁。单纯领取job只锁job，提交后才进入业务；不能在持有job行锁时反过来等settings。并发测试必须验证注销、收藏与run完成不会互相死锁。

模型请求发出前再检查一次当前epoch与取消状态，写回时再检查。已经发给供应商的请求无法靠本地DELETE撤回；取消只尽力关闭网络，迟到正文不保存。使用供应商前需要确认其数据保留与部署配置；首期关闭默认外部trace上报，不把个人原话自动发到第三个观测平台。

30天后清理会话时，清空runs的conversation_id、input_message_id、output_message_id、context_ciphertext和result_ciphertext，填写content_purged_at，再保留额度账本父行到90天。正常创建时会话、输入消息和context必须有值；只有终态且content_purged_at非空才允许清理为空。message型batch同理在终态填写source_purged_at后断开源消息。不硬删仍被账本引用的run/batch。账号注销清正文与偏好后，仅保留有期限的最小调用统计，不再允许登录或重建上下文。

日志仅记录request_id、run_id、step_id、有限错误码、耗时与用量。仪表指标包括队列等待时间、完成/取消/失租数、模型调用量、无候选率、学习延迟、用户纠正率；不把“记住越多”当成功。若需要生产访问私人正文，必须另设计授权与审计，此阶段不给Editor后台直接读取用户对话的权限。

安全切换队列的部署顺序

  1. 关闭创建Agent任务的开关，增加jobs的新列和新索引，保留旧索引供过渡。
  2. 更新普通worker的过滤与所有租约检查，停止或排空旧版进程。旧版进程可能领取新任务，不能跳过这一步。
  3. 启动agent与learning专用进程，验证各自只领取自己的队列，并完成回收过期任务的测试。
  4. 部署新HTTP接口与客户端，再按账号开通A阶段；B阶段另有独立开关和用户同意。
  5. 回滚时先关入口、取消/排空Agent任务，保留新列和队列过滤版worker。不要直接退回会领取所有任务的旧worker，也不要立刻删表。
