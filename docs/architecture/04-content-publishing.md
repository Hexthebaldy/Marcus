# 内容编辑、发布与后台任务

> 本文描述第一版设计，不是已经实现的运行行为。第一版没有Agent。Editor文章与用户Notes使用不同的数据模型和编辑器。

## 1. 编辑人员先选择文章讲什么

餐厅或公园介绍可以只围绕地点，不需要为了发布文章再创建一个“活动”。编辑人员选择地点重心，文章主要对象就是一个地点，详情突出地址、环境、营业时间及到访说明。

演出或展览介绍可以围绕活动。编辑人员选择活动重心，文章主要对象就是一个活动，详情突出作品、演出者、日期、场次、费用和购票说明。场地从活动资料取得，作为活动的辅助信息；尚未确认场地时明确显示“场地待确认”，不用编造地点。

这次选择保存在正在编辑的editor_drafts及提交后的editor_revisions里，字段名为focus_type。地点重心只保存primary_place_id，活动重心只保存primary_event_id，两者不能同时填写。第一版仍是一篇文章对应一个主要对象，不把它扩展成多活动合集。文章可打多个标签，后续搜索再按标签聚合。

创建草稿时可以还没确定重心或主要对象。切换重心时，网页一次提交重心和两个主要对象字段：例如切换到地点重心，同时填写地点编号、清空活动编号。后端在一次保存中检查并替换这组字段。用户不应经历“重心改了，但旧活动还残留”的中间状态；已经公开的版本不受草稿切换影响。

## 2. Editor文章怎样排版和发布

编辑人员使用React网页后台中的专业文章编辑页。编辑页提供标题、副标题、摘要、作者署名、段落、小标题、引用、列表、提示框和分隔线，可以在任意两个正文块之间插图片、图片组或视频，给图片写图注和署名，在文字上添加超链接。实现使用Tiptap和项目明确支持的自定义块，保存前转换为后端约定的JSON。

排版采用几种固定宽度：正文宽度、较宽、占满阅读区。桌面两图并排在手机上变为按顺序堆叠，不能自由设置绝对坐标。这样编辑人员可以制作精细版式，手机仍有确定的阅读顺序。手机阅读页使用受限内容块渲染器和原生视频播放器，不需要安装网页编辑器。首版署名来自文章作者资料。

editor_articles保存文章身份、所属城市、所属区、作者、状态及公开版本编号；editor_drafts保存可编辑正文和工作字段。编辑人员提交时，后端把正文、重心、主要对象、封面和标签复制成固定的editor_revisions，并保存editor_revision_tags、editor_revision_assets及editor_reviews。提交版本的正文不再随草稿变化。

所属区必须属于文章城市，并与主要地点或活动已确认举办地一致；活动尚无确定举办地时可以为空。后端在正式公开时同步更新district_id和公开版本编号，不能因为草稿换了一个区的地点，就提前改变公开文章的区域筛选结果。后续举办地资料更正时，按当前公开文章的关联重新同步所属区。

提交要求非空标题和正文文字；编辑未填写摘要时，后端从正文派生最多500字的摘要。地点重心要求一个公开且正常开放的地点；活动重心要求一个已公开活动，已知场地也必须公开且正常开放。所有已知对象必须属于文章城市。图片和封面均可不提供，实际提供的图片、视频必须ready并允许该编辑人员使用。活动尚未确认场地不阻止文章提交，详情必须明确提示。

审核人员阅读固定的提交版本，查看正文排版、媒体和主要对象资料。批准前，后端再次检查这些公开条件；通过后更新editor_articles.published_revision_id。只有当前公开版本的标签参与公开列表与未来聚合，草稿标签和旧版本标签不能混入。

## 3. Notes怎样创作和发布

普通用户使用手机的标题输入框、正文输入框、相册选图和图片排序。Notes不使用文章编辑器，不提供段落样式、正文指定位置插图、视频或自由排版。标题可不写，正文保留换行。暂定最多5000字和9张图片，至少有非空正文或者一张图片；这些限制是待实测的工程默认。

note_drafts保存正在输入的title、body_text、image_ids和可选地点、活动。它没有document字段。公开的notes直接保存文字与关联对象，note_images保存有序图片。列表封面取第一张图片，无图时cover为null；用户不必单独配置封面。

用户选择活动时不用再重复选择地点；活动有已确认场地时后端补齐地点，同时提交不同地点则拒绝。场地未知时地点可以为空。用户也可以只关联地点或完全不关联对象。关联资料必须公开且与Note城市一致；描述曾经去过的体验可以引用已结束或取消的公开活动。

点击发布时，后端将当时文字、图片顺序和关联对象复制到note_submissions，供审核使用。这份副本只解决“审核的是哪一次提交”，不提供专业文章的历史版本编辑能力，也不使用editor_revisions。审核结果、审核人和理由直接保存在提交记录里。

批准最新提交后，后端在一个MySQL事务里更新notes中的公开文字及published_submission_id、published_at，并整体替换note_images。读取详情时也用同一个一致的读取事务或一条查询取得文字和图片，避免两次读取之间恰好发生更新。first_published_at只在首次发布填写，后续编辑不改变列表中的首次发布时间。

## 4. 两种内容都需要保护已经公开的内容

用户正在重写已发布Note时，读者继续看到notes和note_images中保存的公开内容。编辑人员正在重写文章时，读者继续看到editor_articles.published_revision_id指向的公开版本。两者都隔离草稿与公开内容，但各自使用独立的保存与读取流程。

例如第1次提交已经公开，第2次提交正在审核，第3次提交随后又进入审核。第2次审核即使稍后批准，也只能更新第2次提交的审核结果；后端发现它不是最新提交后，不把它公开。第3次被拒绝时继续展示第1次，不自动倒退选择第2次。

同一用户只有继续保存草稿、没有再次提交时，不影响已经提交的副本；审核仍可按那份副本完成。这意味着“最新草稿保存次数”与“最新提交编号”不能混为一谈。

删除、下架或停用作者后，正在执行的审核不能让内容重新公开。恢复内容是单独的后台操作，需要重新检查选定的已批准提交、关联对象和媒体，不能只修改状态文字。

## 5. 同时编辑和重复提交怎样处理

后端每次保存草稿都增加edit_version。客户端读取草稿时拿到它，再保存时用expected_version发回。两台设备都读取版本5，设备A先保存为6，设备B再用5保存就收到409。客户端保留设备B的本地修改，提示重新读取和人工处理，不静默覆盖。第一版没有多人逐字合并编辑。

提交时客户端传expected_edit_version和Idempotency-Key。后者是同一次请求的唯一编号，断网重试时复用；后端返回原提交结果，不再新建记录。数据库同时限制同一内容编号与based_on_edit_version不能重复，防止客户端换一个请求编号重复提交同一草稿。

两类发布服务分别在事务中锁定主记录、草稿，检查权限和保存版本，再写各自提交副本、媒体关系及审核任务。所有写入一起成功才返回已接受。审核发布时再次锁定主记录、审核记录，检查审核版本和最新提交；所有调用保持固定加锁顺序，避免相互等待。

## 6. 图片与视频存放在哪里

原文件、处理后图片、视频播放文件和视频预览图保存在对象存储。MySQL的media_assets只记录文件位置、用途、类型、大小、处理状态及展示文件资料，不保存这些二进制文件。两类内容共用媒体上传与处理基础能力，但分别校验允许的媒体类型和保存自己的引用关系。Note只能使用作者自己的note_image图片；编辑人员可复用团队editorial_media和place_image素材，不能读取普通用户的私有Note图片；视频仅限editorial_media，文章封面仅限图片，头像仅限本人avatar图片。

人工审核人员拥有的读取范围与素材复用权限不同。moderator或admin在有权查看的固定提交、审核记录或举报详情中，可以读取该对象实际引用的私有媒体，地址短期有效。后端不开放全部私人草稿或素材列表，也不允许把审核看到的用户图片转用于文章。自动检查任务的读取范围同样限于当前任务目标。

上传许可只允许向指定位置上传，在限定时间后失效。上传完成后，后台进程检查真实文件头、大小和解码结果。图片去除位置等附带信息并生成缩略图及详情图。Editor视频接受候选MP4、MOV文件，经过实际格式探测和转码，生成H.264视频、AAC音频的MP4播放文件及预览图。

单视频暂定200MB、5分钟，一篇文章最多5段；处理进程同时校验实际时长及文件大小。这些是工程初值，需要设备和网络测试。视频预览图是该视频的播放辅助文件，不是文章必填封面。处理失败保留可解释原因，草稿提示替换或移除，含失败视频的文章不能提交。

媒体状态从pending进入processing，处理成功成为ready，格式或内容不合格成为rejected，清理后成为deleted。ready只表示处理完成，不表示公开。草稿、审核副本和作者上传文件默认私有，后端验证使用者权限后才签发短期读取地址。

内容公开时，当前公开版本或公开Note中的媒体取得公开展示资格；地点和头像也按各自公开引用判断。审核历史或草稿的私有引用只能阻止文件被过早删除，不能让文件继续公开。下架后如果同一文件还有其他合法公开引用，可以继续服务那个引用；否则停止新地址签发并清除分发缓存。

清理前检查Notes草稿、提交、公开图片，以及文章草稿、版本媒体关系、地点和头像的所有引用。历史数据到保留期并解除引用后，才删除无任何有效引用的文件。视频播放文件和预览图与主媒体一起清理。已经下载到用户设备的公开文件不能保证远程收回。

## 7. 后台进程怎样执行工作

发送验证码邮件、处理媒体和审核辅助检查由独立Python工作进程执行。请求进程先将任务写入MySQL的jobs表，不另部署MQ，也不把整个应用拆成微服务。

| kind | 输入所指对象 | 工作及边界 |
|---|---|---|
| send_verification_email | 邮箱验证记录编号 | 检查验证码仍有效后请求邮件服务商发送。 |
| process_media | 媒体编号 | 根据image或video执行对应处理，不把视频作为图片解码。 |
| review_note | Note提交编号 | 检查简单文字、图片和关联对象，结果只写对应提交。 |
| review_editorial | Editor审核记录及版本编号 | 检查专用正文、媒体和主要对象，进入人工审核。 |
| cleanup | 清理对象种类和编号 | 核查引用与保留期，撤销展示资格并清理文件或记录。 |

任务执行器检查kind与目标对象类型匹配，人工批准仍检查审核人员权限。后台任务不能因获得一个内容编号而绕过文章或Notes各自的发布规则。

工作进程在短事务里锁定待办工作，跳过其他进程已锁定的记录，写入领取者和有效截止时间后结束事务；长时间转码和调用外部服务时不持有数据库锁。MySQL的SELECT ... FOR UPDATE SKIP LOCKED用于这个领取环节，具体语义见[MySQL锁定读取说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

进程执行期间续期，崩溃后其他进程在期限过去后重新领取。执行可能重复，处理输出使用确定位置，发布前检查是否已经完成。任务写回结果还必须验证自己仍持有领取资格，防止旧进程覆盖重新领取后的结果。

发送验证码邮件前重新检查未使用、未过期、未被新码替代。供应商支持请求编号去重时使用固定编号；发送结果未知且不能去重时不盲目反复发送。供应商接受请求不等于已经进入收件箱。验证码通过邮箱发送，用途分别为登录注册和账户注销确认，两种用途不能互换，第一版没有短信任务。

## 8. 用户会看到哪些状态

| 情况 | 行为 |
|---|---|
| 草稿尚未上传成功 | 显示未同步，保留本地内容。 |
| 正文视频或图片处理未完成 | 在对应位置显示处理状态，并说明暂时不能提交。 |
| 活动没有确定地点 | 显示场地待确认，允许合法的活动文章提交。 |
| 地点文章没有活动 | 正常提交，不要求填充无意义活动。 |
| 切换重心漏传关联字段 | 拒绝保存并提示一次提交完整的重心选择。 |
| 新提交被拒绝 | 显示原因，保留旧公开内容。 |
| 标签停用 | 提交时要求调整；既有公开版本可显示历史标签。 |
| 地点关闭或活动取消 | 资料卡显示最新状态，提示编辑复核正文；历史Note可以保留体验。 |
| 无封面或任何图片 | 文字卡片及文字详情正常显示，不产生破图。 |
| 后台处理失败 | 保留可恢复任务或交人工处理，不视为审核通过。 |

## 9. 后续实现的验收场景

第一条流程是上海餐厅的地点文章：只创建地点，编写含副标题、摘要及标签的文章，不创建活动，审核后进入Discover第一Tab。第二条是上海演出活动文章：活动有城市，场地可以待定，页面突出日期和票价；已确认场地后显示真实地点。

第三条是专业排版：编辑人员在两个文字段落之间插图和视频，添加图注、署名、超链接及桌面双图。保存后重开网页编辑器，内容无丢失；手机按同一阅读顺序展示，窄屏没有横向溢出，视频可播放。

第四条是简单Note：纯文字或有序图片可发布，标题可空，没有document、专用封面和视频；修改后等待审核期间旧文字和旧图片保持一致，最新提交批准后一起替换。

并发和关系验证使用MySQL：重复提交只生成一份副本、两人审核不相互覆盖、旧审核不能公开、切换重心原子保存、两个主要对象不能并存、跨城市引用拒绝、无权或未就绪媒体拒绝、处理视频失败可恢复、下架媒体撤销公开资格。本文是设计验收清单，本轮不声称已经执行这些应用测试。
