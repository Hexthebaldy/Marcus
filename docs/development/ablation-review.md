## 删除失败的对照实验

为确认测试能够识别真正必要的保护，另外执行了一次预期失败的实验：

1. 把后端 `src/marcus` 复制到临时目录，通过 `PYTHONPATH` 让独立 pytest 进程加载副本。
2. 只在副本中删除 Notes 审核条件里的 `latest == id`，即不再要求被通过的提交是最新提交。
3. 运行已有用例 `test_old_review_and_rejected_new_submission_preserve_original_public_note`。
4. 测试失败：预期公开文字仍为“已公开版本”，实际却变成了“第二次提交”。第三次提交存在时，迟到的旧审核错误覆盖了公开内容。
5. 检查真实工作树的 `moderation.py` 与实验前逐字相同。副本随临时目录一起删除；真实保护从未移除。

这次实验结果说明，不能把“审核时再检查一次”一概当作冗余。草稿修改、媒体处理、账号状态和审核操作发生在不同时间，中间状态可能变化。

同样保留：权限与私有媒体检查、外部输入校验、发布与审核时的状态复查、版本冲突检查、重复请求处理、数据库失败回滚、任务租约与旧进程写回保护、任务失败记录及重试、登录续期去重、非 JSON 网络错误处理、上传处理超时。工作进程最外层捕获任务异常的用途是记录失败并安排重试，不属于此次删除的“误报成正常业务错误”。

## 验证环境与边界

完整后端测试使用本机 MySQL 的独立 `marcus_test` 数据库、Moto 提供的真实 HTTP S3 接口和独立 `marcus-test` 媒体桶。实际执行了图片上传、旋转、派生图片读取、FFmpeg 视频转码及封面读取，也执行了本地 TCP SMTP 收信测试。限流故障分类使用可控的 Redis 客户端替身，不能据此声称测试了真实 Redis 故障恢复。对象存储异常分类同样通过可控异常注入覆盖。

用户暂不要求前端测试，因此本轮没有浏览器操作、视觉截图、模拟器或真机测试。后端契约测试与前端类型检查不能证明编辑器交互体验，记录中也不作这种推断。

复跑后端时，配置专用测试库，再执行 `scripts/test-backend.sh -q`；需设置 `MARCUS_TEST_S3_ENABLED=1`、`MARCUS_S3_BUCKET=marcus-test`，并启动测试对象存储服务。本轮未修改生产或开发业务库数据，也没有向外部邮箱发送邮件。
